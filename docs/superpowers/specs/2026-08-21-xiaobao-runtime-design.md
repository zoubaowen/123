# 小宝 Agent Runtime 设计

## 1. 背景与目标

小宝学院需要面向学生提供绘画、视频、音乐、游戏、写作和学习辅导能力。个人版 CodeBuddy 不适合作为数百名学生共享的平台后端，按席位采购企业版也不符合项目的长期成本目标。

本项目将完全自研“小宝 Agent Runtime”，不以 CodeBuddy Agent SDK、OpenCode Runtime 或 OpenAgentKernel 作为运行内核。现有 CodeBuddy 与 OpenCode 仅在迁移期保留为应急回退和行为对照，待自研 Runtime 达到验收标准后逐步退出学生主流程。

“完全自研”指自主实现 Agent 循环、Skills 调度、模型路由、工具编排、上下文、记忆、检查点、质量门禁、安全、用量和并发控制。系统仍通过标准接口使用外部大模型、数据库、对象存储和安全沙箱，不重新训练基础模型或重造数据库。

首期容量基线为 300 名注册学生和约 30 个并发任务，但容量不得硬编码。架构需要通过增加 Runtime、队列消费者和沙箱节点平滑扩展到 3,000、30,000 及更多用户。

## 2. 第一阶段范围

第一阶段由小宝 Runtime 接管学生端六个快捷入口：

1. 绘画创作
2. 视频创作
3. 音乐创作
4. 游戏制作
5. 写作表达
6. 学习辅导

自由编程和已有教师后台在第一阶段保持现状。待六入口链路稳定后，再分阶段接管自由编程和更多后台自动化能力。

第一阶段不删除现有 Runtime。任务路由必须保留可配置的旧 Runtime 应急回退，但正常学生流程默认使用小宝 Runtime。

## 3. 总体架构

```text
学生与教师
     ↓
统一 API 网关
     ↓
任务接入层
     ├─ 身份与权限
     ├─ 额度与防刷
     └─ 任务队列
          ↓
小宝 Runtime 集群
     ├─ Agent 核心循环
     ├─ 大师 Skills 引擎
     ├─ 模型路由
     ├─ 工具调度
     ├─ 上下文与记忆
     └─ 质量检查
          ↓
资源适配层
     ├─ 沙箱适配器
     ├─ 数据库适配器
     ├─ 文件存储适配器
     ├─ 模型适配器
     └─ 图片、视频与音乐适配器
```

Runtime 工作节点保持无状态。任务事实、检查点和用量记录写入数据库，媒体与工程文件写入对象存储，短期锁和队列状态由队列服务维护。增加节点即可扩大吞吐量。

## 4. 核心执行流程

每个学生任务按统一生命周期执行：

```text
接收任务
  → 儿童安全与额度检查
  → 识别创作类型
  → 加载对应大师 Skill
  → 判断是否需要追问
  → 形成可执行计划
  → 调用模型和工具
  → 保存步骤检查点
  → 运行与质量检查
  → 局部返工
  → 保存作品
  → 生成学习复盘
```

核心模块职责如下：

- `XiaobaoAgentLoop`：驱动思考、行动、观察和下一轮决策，限制最大轮次、时间和预算。
- `SkillEngine`：发现、校验、加载和执行大师 Skills；记录 Skill 名称、版本和运行约束。
- `ModelRouter`：根据任务能力、年龄、安全、成本和可用性选择模型，并执行受控回退。
- `ToolRegistry`：统一注册工具、参数契约、权限、超时、费用和结果验证规则。
- `ContextManager`：管理即时上下文、摘要和不可丢失的作品约束。
- `CheckpointManager`：保存任务状态和工具成果，使进程重启后可以继续。
- `QualityGate`：验证成果真实存在、可打开、可播放或可运行，并满足 Skill 的专业门禁。
- `SafetyGuard`：处理儿童内容、隐私、危险命令、越权访问和资源滥用。
- `UsageController`：按学校、班级、学生和任务控制 Token、媒体生成及沙箱时长。
- `EventStream`：向前端输出稳定的阶段事件，不暴露内部凭证和敏感推理。

## 5. 大师 Skills 与质量优势

小宝 Runtime 的主要竞争力不是重复普通编程助手，而是稳定执行适龄、可验证的专业创作流程：

- 六个学生入口默认加载唯一对应的大师 Skill。
- 学生只回答真正影响结果的少量问题，技术配置由 Runtime 完成。
- 视频必须经过角色设定锁、角色参考图、连续性表、九宫格、学生确认、逐镜生成和粗剪检查。
- 游戏必须真实启动、试玩并覆盖操作、碰撞、计分、胜负和重开。
- 图片、音乐和视频只有真实工具结果通过查看或试听后才可称为成品。
- 写作和学习辅导保留学生原创参与，不代做可直接提交的作业。
- 修改采用局部返工，保护已经通过检查的部分，避免浪费生成费用。
- 低成本模型处理普通步骤，高能力模型只用于难点和质量复核。
- 后续可引入策划、执行和审核角色协作，但第一版先保证单 Agent 主循环稳定。

## 6. Provider 接口

Runtime 不得把供应商写入核心逻辑。所有外部能力通过稳定接口提供。

### 6.1 模型

`ModelProvider` 负责模型发现、流式调用、结构化工具调用、Token 统计、取消和错误归一化。首批适配 OpenAI 兼容协议，并逐步支持 DeepSeek、混元和豆包等服务。

### 6.2 沙箱

`SandboxProvider` 负责创建、执行、文件读写、端口预览、快照、恢复和销毁。支持从开发期受限执行器演进到单机 Docker、多服务器容器池和 Kubernetes。

Runtime 本身禁止直接运行学生代码。学生任务使用独立工作目录、临时凭证、资源限制和网络策略，不能访问数据库、模型密钥或其他学生文件。

### 6.3 数据库

`DatabaseProvider` 保存用户、班级、课程、任务、事件、检查点、用量和作品元数据。开发期可使用 SQLite；正式环境推荐 PostgreSQL，同时保留现有 CloudBase 数据迁移或兼容能力。

### 6.4 文件存储

`StorageProvider` 负责上传、下载、签名 URL、版本、删除、容量与校验和。开发期使用本地目录，正式环境可使用 MinIO、腾讯 COS 或任意 S3 兼容服务。

### 6.5 媒体服务

图片、视频和音乐分别使用独立 Provider。视频首选火山引擎，但角色一致性、九宫格和连续性属于 Skill 与 Runtime 质量契约，不能依赖某个供应商才能成立。音乐供应商未确定前只生成制作蓝图，不伪造音频成果。

## 7. 自有服务器部署演进

初期可在一台服务器部署：

- 小宝 Runtime
- PostgreSQL
- Redis 或兼容队列
- MinIO
- Docker 沙箱执行器
- HTTPS 网关

用户增长后逐步拆分为 Runtime 集群、数据库节点、存储节点、队列节点和沙箱服务器池。部署拓扑变化不得影响学生 API、任务格式、大师 Skills 或作品数据契约。

## 8. 状态机与恢复

任务状态采用显式状态机：

```text
created
  → safety_check
  → requirements
  → planned
  → running
  → waiting_for_student
  → quality_check
  → revising
  → completed
```

异常可进入 `retrying`、`paused_budget`、`failed_recoverable`、`failed_terminal` 或 `cancelled`。状态转换必须幂等，并记录版本号，防止重复消费者同时推进同一个任务。

检查点至少保存：

- Runtime、模型和 Skill 版本
- 学生原始要求及已确认约束
- 计划和当前步骤
- 工具调用、验证结果和费用
- 已生成文件的稳定标识及版本
- 上下文摘要和下一步恢复指令

## 9. 错误处理

- 模型超时：指数退避重试，再按策略切换兼容模型。
- 工具失败：只重做失败步骤，不清除已验证成果。
- 单个镜头或媒体片段失败：局部返工，不重做整个作品。
- 沙箱崩溃：使用最近快照在新实例恢复。
- 数据库不可用：停止无法保证一致性的写操作，不返回虚假成功。
- 存储失败：保留临时结果并标记未交付，不把临时地址当成最终作品。
- 预算超限：暂停高价步骤，允许教师审批或选择低成本路径。
- 不适龄内容：拒绝危险部分，并提供安全、可创作的替代方向。

## 10. 容量与成本控制

容量通过配置和资源配额控制，不在业务代码中写死：

- 轻任务、媒体任务和沙箱任务使用独立队列。
- 教师课堂可配置更高优先级，但不能突破学校总预算。
- 并发超限时排队并展示状态，不直接丢弃任务。
- 每个学校、班级、学生和任务均可设置额度。
- 节点故障时未完成任务回到队列，由其他节点从检查点恢复。
- 初期目标为 300 名用户和 30 个并发任务；后续通过增加节点扩展到 3,000、30,000 及更多用户。
- 后续支持多学校租户隔离、独立资源池、跨地域部署和异地容灾。

## 11. 安全与隐私

- 前端不得获得模型、数据库、存储或沙箱凭证。
- 日志遵守仓库安全规则，不记录动态敏感值。
- 学生私密资料与可公开作品分离存储。
- 所有工具声明权限级别和数据访问范围。
- 文件进入永久存储前检查类型、大小、恶意内容和安全策略。
- 高风险操作需要明确的教师或管理员授权。
- 数据库和存储建立备份、保留和实际恢复演练机制。
- 为未成年人场景预留监护人同意、数据导出和删除能力。

## 12. 兼容与迁移

现有任务 API 和前端事件尽量保持兼容。新增小宝事件使用版本化信封，允许旧前端忽略未知事件。现有 CodeBuddy/OpenCode Runtime 在迁移期作为独立适配器存在，不允许其内部类型泄漏到小宝 Runtime 核心领域模型。

六入口先灰度接入小宝 Runtime。出现明确的可恢复故障时，可以按管理员策略回退旧 Runtime；不得在学生不知情的情况下重复收费或重复生成作品。

## 13. 测试与验收

开发采用测试先行。每轮必须执行相关单元测试、类型检查、代码规范检查和构建；学生可见流程必须在浏览器真实操作。

第一阶段验收标准：

1. 六个学生快捷入口默认进入小宝 Runtime。
2. 任务能够加载正确的大师 Skill。
3. 前端能稳定接收任务阶段和工具事件。
4. 至少一种真实创作工具完成端到端调用。
5. 任务步骤、结果、用量和检查点能够持久化。
6. 服务重启后可以从检查点继续任务。
7. 失败工具可局部重试，不重复已完成高价步骤。
8. 教师可查看和限制学生用量。
9. 可配置切回旧 Runtime 进行应急处理。
10. 完成 30、100、300 并发的分阶段压力测试，并记录硬件与结果。

## 14. 分轮日志规则

每完成一轮工作必须：

1. 更新 `docs/progress/2026-08-21-xiaobao-runtime.md`。
2. 记录本轮目标、实际改动、测试与浏览器验证结果。
3. 记录提交编号、未完成事项、已知风险和下一步。
4. 只暂存本轮明确文件，避免提交现有工作区的无关改动。
5. 创建独立 Git 提交，保证可以定位和回退。
